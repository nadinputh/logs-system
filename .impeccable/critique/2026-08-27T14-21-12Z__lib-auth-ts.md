## Priority Issues Remaining

### [P1] CSRF coverage not complete — 2 mutating routes still lack `assertSameOrigin`
- `app/api/auth/passkey/[credentialId]/route.ts` DELETE — cross-origin forge can delete a signed-in user's passkey (denial-of-MFA). **[fixed post-critique]**
- `app/api/teams/invites/[token]/accept/route.ts` POST — cross-origin forge can make a signed-in user accept a team invite they never saw. **[fixed post-critique]**

### [P1] Active-sessions card is misnamed and self-contradicting
Title implies a list; body is one button. Preamble promised "you'll be signed back in on this device" while the confirm banner promised "you'll be sent to the login page" — the second is true. **[preamble reconciled with reality post-critique]**

### [P1] `POST /api/auth/reset-password` bypasses `bumpSessionsVersion`
Uses `$inc` directly on `User.updateOne`, so the current Node process's cache still holds the old `sv`. A 60-second window on the process handling the reset is the wrong process to have a window on. **[fixed post-critique: routed through helper]**

### [P2] `POST /api/logs` still silently swallows its own auth error
`if (auth.error && actorSession) return auth.error;` — if `actorSession` is null, `auth.error` is dropped. Intended for visitor check-ins but reads like a bug.

### [P2] Nothing binds `PreAuthToken` to IP/UA; kiosk JWT has no `jti`
Both were noted last run; both still open. 15-second kiosk QR is infinitely replayable within its window.

## What Improved Since Run 1

- **Session revocation channel exists.** `User.sessionsVersion` stamped on JWT at sign-in, verified per-request via a 60s read-through cache in `jwt` callback; `bumpSessionsVersion` primes the cache from inside.
- **Session `maxAge` explicitly 14d** (was 30d default). 14d + revocation vs 30d + none.
- **`/terminal` fix is exemplary** — middleware branch removed with a headstone comment; page guarded via `app/terminal/layout.tsx` using team role.
- **`?reason=` mechanism** in `requireTeamPageAccess` — 5 codes: `no_active_team | removed | suspended | team_deleted | insufficient_role`. Team-deleted case reconciles stale `activeTeamId` on read.
- **Member removal unsets target's `activeTeamId`** if it matched, so no redirect loop.
- **`assertSameOrigin` wired into 35 of 37 mutating routes** (35/37 → now 37/37 post-critique).
- **"Sign out other devices" control** on `/settings/passkeys`.

## Genuine Strengths
1. `?reason=` mechanism is well-designed and non-leaky. 5 codes, each with copy that names the truth without exposing anything.
2. Revocation cache is honest — documents its stale-token window explicitly, refuses to await in hot path, primes from inside `bumpSessionsVersion`.
3. `/terminal` fix pattern — the whole app should imitate it.

## Persona Red Flags
- **User whose phone was actually stolen:** revocation exists but is under `/settings/passkeys` (curious home), no device inventory, up to 60s window on remaining validity. No per-device kill.
- **User whose password was reset by admin:** signed out globally, correctly, but the reset-serving process held stale `sv` for up to 60s in its cache. **[fixed]**

## Minor Observations
- Kiosk JWT still lacks `jti`; `signKioskToken`/`signSessionQrToken` don't set `sub` or `aud` claims.
- `readSessionVersionCached` returns `null` on cold cache — a rotating fleet never enforces `sv` on first hit per pod.
- Signout endpoint leaks `sessionsVersion` to the client — harmless implementation detail.

## Provocative Questions
1. If the claim is "compliance-grade revocation," what regulatory framework accepts a 60-second window between "the button was pressed" and "the compromised token is dead"?
2. Why is the revocation control filed under `/settings/passkeys` instead of `/settings/security`? A user who has never registered a passkey has no reason to visit that page.
3. Given `/terminal` was wrong precisely because middleware read the system role and the truth was in the team role — how confident are we that `/dashboard`, `/admin`, `/logs`, `/profile` haven't got the same class of bug?
